## 三、根因解剖：为什么「全配对却没有下一关按钮」

用户截图里四种目标字全部凑满（枪 3/3、棍 2/2、锤 2/2、钩 2/2），**却没有任何按钮**。
排查结论：**胜负判定本身没问题**，问题出在"判完之后往哪儿去"。

```ts
// GamePage 通关时的动作（大意）
this._finished = true;  this._busy = true;      // ← 先把两个闸刀合上
PageManager.goto(PAGE_CLEAR, res);              // ← 然后请求切页
```

而 `PageManager.goto` 的实现是**查表 + 静默返回**：

```ts
const Ctor = this._registry.get(name);
if (!Ctor) { log(`[PageManager] 未注册的页面：${name}`); return; }   // ← 就是这里
```

当时 `PAGE_CLEAR`（值 `'clear'`）**从未被注册**（`GameRoot` 里只注册了 boot/home/chap/map/game），
于是：`goto('clear')` 打一行日志就 `return` —— **不抛错、不降级、不切页**；
而此时 `_finished` / `_busy` 已经双双置位 → **对局页彻底冻死**（拖不动、点不动、也没有按钮）。

三种"看起来合理"的错判，都不成立：

| 怀疑 | 为何不成立 |
|---|---|
| 胜负判定没触发 | `[Diag] STATE seq=10 通关 步=9 已消=9/9 剩牌=0` 白纸黑字 —— 判定**确实触发了** |
| `goto` 抛异常被吞 | 没抛。`未注册的页面` 是 **log 不是 error**，`try/catch` 抓不到 |
| 按钮画了但被遮挡 | 压根没有这一页 —— 页面节点都没创建 |

**修法**（两处）：
1. 新建 `ui/ResultPage.ts`（`readonly pageName = PAGE_CLEAR`）：星级逐颗 pop、副标题按星数、三项统计（用时 / 挪动 / 成字）、拆字回放、独立的「下一关」按钮。
2. `GameRoot` 里 `PageManager.register(PAGE_CLEAR, ResultPage);`。

**顺带修的一处同类隐患**：`PAGE_FAIL`（`'fail'`）**同样从未注册** —— 时间到的失败分支走的也是 `goto('fail')`，症状一模一样。这条按用户拍板改成了弹层（下一节），并在 `GameRoot` 里留了注释写明"**刻意为空**"，避免后来者以为是漏注册又补上一个（那会退回到"切页 → `destroy()` 掉对局节点 → 盘面状态丢失"的老坑）。

**「下一关」判据**：走 `canPlay(nx)`（**可玩 AND 本章已解锁**），不是简单的 `n+1 <= LEVELS.length` —— 否则首版只开放 1~3 关时，L3 通关会点进 L4 的空白页。

## 四、失败页为什么必须是「页内弹层」，而不是独立页

原本的设计是独立页 `FailPage`。**行不通**，原因是 `PageManager` 切页时会 `destroy()` 掉当前页整棵节点树：

- 对局页节点一旦销毁，`_board` 的牌位、`_left` 的剩余时间、已消进度**全部随之消失**；
- 而「看视频复活」的全部意义就是**保住盘面** —— 复活回来必须还是那 22 张牌、原位置。

所以按拍板改成**对局页内的常驻弹层** `ui/FailGate.ts`：只是把一层半透明遮罩 + 卡片挂到对局页根节点上，**对局节点一个都不动**。

**弹层三个按钮的实测设计坐标**（截图量取，命中即触发）：

| 按钮 | `d:` 动作 | 触发结果（控制台原文） |
|---|---|---|
| 看视频复活 | `d:0,-90` | `[GamePage] 请求激励视频（复活 +30 秒）` → `[FailGate] 关闭` → `[GamePage] 复活成功：时间 +30 秒，盘面剩余 18 张牌` |
| 重来一局 | `d:0,-200` | `[GamePage] 重来一局 → L3` → `[PageManager] 进入页面 game` → 重新弹出 |
| 返回地图 | `d:0,-304` | `[PageManager] 进入页面 map` |

**复活链路完整日志**（`冒烟控制台-失败复活.txt`）：

```
[GamePage] L3 时间到：还剩 18 张牌未合，成字 0
[Diag] STATE seq=2 失败 步=0 已消=0/9 剩牌=18
[FailGate] 弹出：时间到了 / 看视频复活
[GamePage] 请求激励视频（复活 +30 秒）
[FailGate] 关闭
[GamePage] 复活成功：时间 +30 秒，盘面剩余 18 张牌
[Toast] 复活成功，时间 +30 秒
[Diag] STATE seq=3 复活 步=0 已消=0/9 剩牌=18
```

**两条最关键的硬证据**：

1. **盘面零损耗**：复活前后各打了一次 `[Diag] TILES` —— `彳@0,0,junk 匚@0,1,junk 木@0,2,radical … 昆@4,5,part`，
   **22 张、逐字完全一致**。这正是选弹层方案的目的（若走独立页，这里会是一张全空的盘）。
2. **复活给的是新的完整 30 秒**，不是"补一点"：复活后**再干等 9 秒**断言 `gate:时间到了` → `gatesOf()` 报"本局弹出过 **1 次**"。
   即 9000ms < 30000ms，没有立刻再失败。（若复用 `forceTimeLimit` 的 6 秒，9 秒后必弹第二次。）

**弹层文案与 `AdGate`（死局重排）刻意同构**，便于工装用同一套正则 `gatesOf()` 抓：

```
[AdGate ] 弹出：卡住了   / 看广告重排      ← 死局
[FailGate] 弹出：时间到了 / 看视频复活      ← 失败
                └───────┬───────┘
          正则 /\[(?:AdGate|FailGate)\] 弹出：(.+?)\s*\/\s*/  ← 同一个
```

> ⚠️ **改版式必须重算这三个 `d:`** —— 它们由 `FailGate.ts` 顶部的 `CARD_H` 逐行相加得出
> （`CARD_W=300 / PAD_X=22 / BTN_W=256`）。顶部常量动一行，这三个值就全废。
> 旧文档里写的 `d:0,-25` 是改版前**估算**的，从未与代码对上过（点下去落在说明行上）。

> ⚠️ **断言只能用 `th:复活成功`（Toast 第一行）**。降级说明
> 「（未接入广告位，直接发放）」在**第二行**，而 `toastOf/toastsAll` 只取第一行 → `th:未接入广告位` **必然失败**。

## 五、手感三处怎么取证：**录屏，不要单拍**

这是本轮工装侧最重要的经验，写在这里免得以后重踩。

**单张 `Page.captureScreenshot` 从发请求到真正成像要 50~190ms**。整屏 600×1260 实测：
请求 +0ms 的那一张，"帧落在 +0~125ms"。而合并撞击的**挤压窗口只有 70ms** ——
**单拍的时间分辨率比事件本身还粗**，拍不拍得到全看运气。

于是给冒烟工装加了 **`Page.screencastFrame` 录屏**（`rec:on` / `rec:off[:<name>]`），
拿到"帧序列 + 每帧到达时刻"。实测 **181 帧 / 3011ms ≈ 59.8 fps（满帧）**。

三个必须记住的坑：

1. **必须逐帧回执** `Page.screencastFrameAck`。不回执，Chrome 认为前端消费不过来会**静默停推流** ——
   表现是"录了 3 秒只拿到 1 帧"，且**没有任何报错**。
2. 用 **jpeg quality 85**。PNG 编码一帧要几十毫秒，会把帧率压到个位数。
3. **⚠️⚠️ 录屏期间绝不能同时单拍。** `Page.captureScreenshot` 会**抢占合成器**，
   抓图那段时间 Chrome 不产新帧 → 录屏流出现**成片黑帧**，而撞击那几帧正好落在连拍最密的一段。
   症状极具误导性：时间轴上看起来"牌已经坐好不动了"。
   → 为此给 `impact` / `tapfx` 都加了 **`none` 变体（只动不拍）**，录屏取证一律用它。

另外两条与"抓不到动效"直接相关的工程细节：

- **连拍补偿必须按真实耗时算**，不能累加"请求值"。用 `shotClip`（CDP `clip` 只抓一块区域）把单张
  从 125ms 压到 **58ms**：裁到"拖拽那一带"（约 600×160 = 96k 像素，vs 整屏 756k）。
- **`impact` 的裁剪框要留够余量**（`PADPX = cellPx * 1.6`）。第一版只留 60px（≈0.7 格），
  结果"丈从 col3 挪到 col2"时**把搭档漏在框外**（搭档在 col1、屏幕 x=160，框却从 193 开始）
  → 撞击帧里只看得见丈自己，看不出"两张牌撞在一起"。

## 六、拖动跟手 —— 像素级量化（`量化-拖动跟手.txt`）

**数据源**：`/tmp/s5-feel2/11-feel-mid.png` —— 拖到插值 60%、**松手前**截的那一帧（整屏 600×1260）。
**场景**：L3（`seed:1`）第一次拖拽，`[Diag] SUGGEST` 从=`丈@3,3` 到=`3,2`，即 丈 从「列3」挪到「列2」，同一行（设计 y=−164）。

坐标口径：原点左上、画布 600×1260、中心 (300,630)；设计单位→屏幕 px 缩放 `PS = 600/720 = 0.8333`。

```
【参照值】
  起点格中心  x = 346.7      （设计 x = +56）
  目标格中心  x = 253.3      （设计 x = −56）
  两者相差      93.3         （= 一格 112 设计单位 × 0.8333）
  拖拽插值 10 段、midAt = round(10×0.55) = 6 → 实际进度 60%
  → 60% 时手指应在 x = 346.7 + (253.3−346.7)×0.60 = 290.7

【实测】按"纸面亮区"（亮度≥205）分段测量被拖那张牌：
  纸面段 x 244..337，宽 93，中心 290.5
  （宽 93 = 一格 85.0 × 1.1 —— 与 DRAG_SCALE 1.1 的"拎起来"状态吻合）

【结论】
  | 与手指位置   290.7 | 差 −0.2 px | ← 跟手 |
  | 与目标格中心 253.3 | 差 +37.2 px | ← 不是吸附 |
  | 与起点格中心 346.7 | 差 −56.2 px | ← 不是吸附 |
```

→ 牌停在**手指所在的位置**（误差 0.2px，小于 1 个像素），**不是**"一格一跳"地吸附到某个格中心。
这正是把 `onMove` 从「`setPosition(整数格中心)`」改成「沿锁定轴用手指真实位置 + 另一轴锁死 + 越界橡皮筋」的效果。

**橡皮筋**：越界用 `rubber(M, over) = M · over / (over + M)` —— 渐近饱和，越拉越沉、松手弹回，
不是硬夹到边界（硬夹的手感是"撞墙"）。

配套图 `实拍-手感-拖动跟手-标注量化.png`：蓝线 = 两个格中心（346.7 / 253.3）、红线 = 手指应在位置（290.7）、
绿线 = 实测牌心（290.5）—— 与红线几乎重合。

## 七、点击微反馈 —— 波纹确实渲染了（`实拍-手感-点击波纹-差分放大.png`）

**同时有"拎起来"和"波纹"两层**：
- 第 1 层（`onDown`）：80ms 放大补间（视觉上牌被"拎起来"）+ 该格一圈扩散波纹 `rippleAt()`；
- 第 2 层（`onUp → tapTile`）：按结果分支 —— 能消 → 撞击动效；能配但未对齐 → toast + `pulseTiles` + `rejectTile`；干扰牌 → `rejectTile`。

**这条曾被我连续误判两次**（都得出"波纹完全不可见"），值得记下来：

| 误判 | 判据 | 为何错 |
|---|---|---|
| ① | 「金色度峰值」（恒 21.5 不动） | 这次点的是**干扰牌**，波纹用 `INK3`（墨灰）—— **本来就没有金色** |
| ② | 「牌格内帧间差」（+186~+252ms 恒 0） | 取样框只取到**牌格内**，而波纹很快长到牌**外面**去 |

**最终判据**：帧间差异像素的**包围盒** → `x 103-216 / y 617-729`；牌格是 `116-204 / 629-717`
→ 环在牌**外沿约 13px**。按 +252ms 的 k=0.814 反算，环外沿应落在 `102.5~217.5`，**与实测完全吻合**。
**峰值亮度对比约 30/255** —— 属"柔和"，符合你要的"小小提示"。

> 第 2 层「拎起来」在 `tapfx:pair` 的帧里肉眼可见（牌明显放大）。
> ⚠️ 实测踩到一条反直觉事实：**`SUGGEST` 的起点牌不一定没有已对齐的搭档** ——
> 盘面上可以**同时**存在一对已对齐、只等玩家点一下的牌（`[Diag] REACH direct=1`）。
> 所以轻点起点牌真的会把它消掉（实测 `STATE seq 2→3`），但**步数不变**
> （`resolveMatch` 只在拖动路径上计步）。→ 硬断言请默认点**干扰牌**（必然拼不成字，可逐项不变）。

> ⚠️ **挤压（`IMPACT_SQUASH=1.18` / 0.82，仅 70ms）在 60fps 帧流里也难单独分辨** ——
> 它与"合成字浮现"占同一时间窗。这一条**如实记录，不当作已验证**：

**另一条必须写进注释的引擎坑**：`shakeBoard()` 震的是**棋盘节点**，而它是牌的**父节点** →

## 十二、写这份 README 时**自己踩到的两个坑**（留档，因为都是"安静失败"）

写文档时我按记忆把命令抄了一遍，跑出来两条失败。两条都不是游戏的问题，是**命令写错了**：

### ① `th:妙手成字` —— 把「结算页副标题」当成了 Toast

```
❌ 提示断言失败（历史）：本局从未弹过包含「妙手成字」的提示，实际弹过 0 条：「」
```

「妙手成字」是 `ResultPage` 里按星数取的**副标题**（`TITLES[stars]`），**从来不是 Toast**。
通关时**一条 Toast 都没有** → 这条断言**永远不可能通过**。

**正解**：通关链路只用 `p:clear`（它断言 `[PageManager] 进入页面 clear`，是硬断言）。
`p:<页面名>` 取自 `PAGES.ts`：`boot / home / chap / map / game / clear / fail / atlas / set`。

### ② `time:6` 放在了 `p:game` 后面 —— 静默失效

```
我的命令  → [GamePage] L3 开局就绪：… 限时 142s · 种子=force:4     ← 6 秒没生效
归档那次  → [GamePage] L3 开局就绪：… 限时 6s(force，关卡表是 142s) · 种子=force:4
```

`time:` 的注释里白纸黑字写着 **「必须在 `unlock:` 之后、进入对局页之前（`GamePage.onCreate` 读一次）」**，
`seed:` 同理 —— 两个都是**写全局变量、由对局页读取一次**。放到 `p:game` 之后就只是**安静地无效**：
不报错、不警告，你会干等一场根本不会弹层的 8 秒。

**正解**：`unlock:3 wait:2200 seed:4 time:6 … p:game wait:8000 gate:时间到了 …`
**自检点**：看「开局就绪」那行是不是 `限时 6s(force…)`；显示 142s 就是放晚了。

> 两条都是**同一类病**：**断言/参数写错时不会报错，只会"什么都不发生"**。
> 所以新增回归命令后，**必须实跑一次并肉眼核对那一行关键日志**，
> 不能凭"看起来对"就写进文档 —— 否则坑的是下一个照抄的人（包括三个月后的自己）。
