# S16 · 部件「靠边」重制 + 推箱机制

用户 2026-10-03 本轮原话（两条大需求）：

> 1、偏旁和部首要靠边，比如竹字头，不要以竹字来表示，别人看不懂，而且要放在格子的上半部分；
>    比如弓字，要靠格子的下半部分，类似的字体都要重新渲染；
> 2、把每次允许推着相邻的格子一起动……当两者消掉后，革字比原来往右移动了一格
>    （必须要达成消除条件，才允许这样推，不然会回到原来的地方），
>    当遇到原来不相连的障碍物时，要被挡住。

拍板（AskUserQuestion）：靠边口径 = **② 靠边轻缩 0.72**；贴哪条边 = **各靠自己那半边**；
推的格数 = **可中途停、但必须与 A 达成消除条件**；规则改动力度 = **全量重跑，稳妥**。

## 一、需求 1：部件靠边（131 个部件半边表 + 重烘 256 张贴图）

### 1.1 「靠哪半边」是一份**算出来的数据**，不是渲染时猜的

新增 `design/tile-roles.js`（8,674 字节，**生成物，勿手改**；生成器 `tools/gen-tile-roles.py`）。
它给出每个部件的角色，`design/ink-tile.js` 只负责把角色翻译成坐标：

| 角色 | 含义 | 个数 | 代表部件 |
|---|---|---:|---|
| `t` | 贴格子上半（字头） | 9 | 竹 艹 宀 户 雨 父 分 奴 沙 |
| `b` | 贴格子下半（字底） | 32 | 弓 前 斤 皿 羽 子 平 韦 龙 … |
| `l` | 贴格子左半（左旁） | 19 | 木 氵 钅 犭 虫 禾 日 巾 土 … |
| `r` | 贴格子右半（右件） | 70 | 仓 刂 鸟 马 月 丁 云 京 少 … |
| `c` | 居中满格 | 1 | 方（信息不足，**不猜**） |

### 1.2 判定方法：**模板匹配**，不是启发式

把合成字按分界线切成两个半块，两个半块各自与 `a`、`b` **单独**的字形比形状
（都归一化到 128×128 再算 IoU）；切法试 4 种（a上b下 / b上a下 / a左b右 / b左a右），
总分最高的胜出。这一条**同时**回答「上下还是左右」和「a 在哪半边」。

- 145 个合成字的匹配分数差（margin）中位 **0.28**；
- 最小的 4 个（莲 / 房 / 扉 / 蓉，margin ≤0.02）**人工修正**，理由逐条写在生成器的 `OVERRIDE` 里。

**★ 走进又退出的两条错路（留档，别再走回去）**
1. 「a 的墨迹宽 / b 的墨迹宽 ≈ 分界线位置」—— **信息量为零**：a、b 单独渲染时各自都撑满 em 框，
   比值恒 ≈ 0.5，与它们在合成字里真实占多少毫无关系。
2. 投影谷（竖直投影找山谷当分界）—— 只是旁证，笔画交错时必误判
   （波 / 弧 / 靶 / 鲸 / 花 / 莉 都被它判反过）。

### 1.3 汇总回「部件」的两条关键口径

1. **只让上过棋盘的字投票** —— 145 条拆字表里只有 117 条真被关卡用到。
   「涟」没上过棋盘，不用这条时它会把「连」投成居中。
2. **按关卡出现次数加权**，不是按「出现在几个字里」。

> **★ 这条独立算出来的规则，正好撞上用户的手工预期。**
> `弓` 按字数是 1:2（弩 vs 弦/弧），按关卡次数是 **8:6**（弩占 L1~L8）⇒ 落在「字底」，
> **正好等于用户点名的「比如弓字，要靠格子的下半部分」**。生成器里把它写成了硬断言。
> 规则与人工预期撞上，是对这条规则最好的验证。

### 1.4 竹字头：字体里没有 ⺮，只能裁剪合成

马善政（Ma Shan Zheng）7015 个码位里**没有** `⺮`（U+2EAE，实测确认）。
系统宋体有真 ⺮，但**系统字体不可随产品分发**。
所以把「竹」的下半截用 `clipPath` 裁掉，保留上半截 —— `keep=0.62`
（与宋体真 ⺮ 的放大对比条选出来的）。

⚠️ `clipPath` 必须挂在字形坐标系的**内层 `<g>`** 上：外层 transform 之后，
内层 g 的坐标就是字形坐标，裁切矩形可以直接用 `box` 的单位写。id 里带 `hash(ch)`，
避免同页多张牌互相顶掉。

### 1.5 渲染侧改动（`design/ink-tile.js`）

```js
var FIT = 0.76;          // 合成字：居中满格
var PART_SCALE = 0.72;   // 部件：先缩到 72%，再贴向它所属的那半边
var PAD_EDGE = 62;       // 贴边留白
```

部件在合成字里本来就只占半边；不缩的话「木」贴左后仍是 76% 画心那么大，
会顶到格子中线甚至越界。

## 二、需求 2：推箱（允许推着相邻的格子一起动）

### 2.1 规则落点（真源仍是 `core/Board.ts`）

| 位置 | 改动 |
|---|---|
| `Board.slideRange` | 从「碰到牌就停」改成「先越过连续被占的一整段 → 再数后面连续的空格数 k → 最远停在当前位置 + k 格」。返回值形状不变 ⇒ `reachableCells` / `clampSlide` / `canSlide` / `findSuggest` / `findNonMatch` / `findTreasureMove` **全部零改动** |
| `Board.dragMoves` | **唯一**回答「被推的牌去哪儿」，返回一整段刚性平移的 `CellMove[]` |
| `Board.applyDrag/undoDrag` | **必须先全清 `from` 再全写 `to`** —— 整段平移时两个集合重叠，边清边写会把还没搬走的牌擦掉 |
| `Solver.stateKey` | 必须带坐标（`id@r,c`）：推箱后牌会搬家，只记 id 会把两个盘面当成同一个，记忆化剪枝静默漏解 |
| `Solver.listActions` | 去重键必须带落点：`t.id + ':' + hit.id + '@' + x.r + ',' + x.c` |

用户拍的额外半句「**只要不推到最远也允许在中途停下，但必须要有元素与 A 达成消除条件**」，
在引擎里就是原有的**严格回弹**：落位凑不成字 → 整段沿原路弹回、步数不变。

### 2.2 本轮新增加固：样本要挑「这一推**新造出**的配对」

第一版 `findPush` 只要求「落位后 `matchTargets` 非空」，于是 L3 的 A 样本回回是
「玄@4,5 → 3,5，命中 弓@6,5」—— 可这两张**拖动之前就同列、中间无遮挡**，本来就已对齐
（`REACH direct=1` 那条就是它）。那种样本下「凑成字」根本不是这一推带来的，
A 段断言等于只验了「被推的牌会动」。

现在先算一遍 `preHits`（**拖动之前**与该牌对齐的那些），落位后的命中只有在
**不在 `preHits` 里**时才算「新造的」，优先返回它。

### 2.3 可测入口（每个硬断言都有游戏侧打印的 `[Diag]` 行）

| 行 | 来源 | 种子 |
|---|---|---|
| `[Diag] PUSH` | 推着走、**落位凑成字**的走法 | `DIAG_PUSH_SEED = 20261004` |
| `[Diag] PUSHNM` | 推着走、**落位凑不成字**的走法 | 同上（三行各用不同常量，共用会让随机流互相偷走） |

⚠️ 诊断行里的命中坐标是**推完之后**的：`findPush` 内部是「整段位移 → 判定 → 倒放回去」，
`hit.r/hit.c` 上挂的仍是拖动前的坐标，要显式换算。

### 2.4 冒烟 `push:` 断言（A / B 两条，缺一不可）

- **A**：按 `[Diag] PUSH` 拖一手 → 断言**被推的那串牌永久停在新位置**
  （步数 +1、已消 +1、每张被推的牌在预测的 `to` 格上）
- **B**：按 `[Diag] PUSHNM` 拖一手 → 断言**整段沿原路弹回**
  （步数不变、`[Diag] TILES` 逐字还原、有 `严格回弹：` 日志）

> 只验 A，「必须达成消除条件才允许这样推」那半句没验到；
> 只验 B，「推得动」本身没验到。而这两件事在**推箱之前都测不出来**。

### 2.5 实测证据（L3，`seed:1631370480`）

```
[1]A 推箱合成：拖「竹」(0,2) → (3,2)，被推 玄@1,2→4,2
   ✅ 被推的 1 张全部停在新位置（玄@4,2），步数 0→1，已消 0→1
[1]B 推箱回弹：拖「铁砧」(3,4) → (2,4)，被推 奴@2,4→1,4
   ✅ 整段 1 张全部回到原格，步数仍为 1
[2]A 推箱合成：拖「弓」(5,2) → (1,2)，被推 玄@4,2→0,2
   ✅ 被推的 1 张全部停在新位置（玄@0,2），步数 1→2，已消 1→2
[2]B 推箱回弹：拖「玄」(4,5) → (4,4)，被推 父@4,4→4,3、火@4,3→4,2
   ✅ 整段 2 张全部回到原格，步数仍为 2
   小结：通过 4 条，失败 0 条，跳过 0 条
```

第 2 轮 A 正是用户描述的那种情形：**「弓」往上推，「玄」被推到 0,2 与它相邻凑成「弦」**；
B 则是「玄」推着「父」「火」两张走、推到边界停住。

**样本供给普查**：38 关 × 每关 4 颗种子 = 152 盘，**全部**同时具备 `PUSH` 与 `PUSHNM` 样本
（`M N`）。L1（6×6）也有 —— 所以 `push:` 不必特意挑大关卡。

## 七、本轮修掉的 3 个工装 bug（都极具误导性，留档）

1. **`const { geo, smp } = awaitGeo(...)` 漏了 `await`。**
   `awaitGeo` 是异步的（要轮询等棋盘建好），少写一个 `await`，解构得到的是 Promise 本身，
   `geo`/`smp` 恒为 `undefined` ⇒ 每轮都报「拿不到棋盘几何」。
   而**同一时刻直接调 `parseBoardGeo` 明明是好的** —— 所以第一反应会去翻解析器，方向全错。
   教训：从同步函数（`chaiziReboundTest`）照抄骨架时，最容易丢的就是 `await`。

2. **`lastDiag(cdp, '[Diag] PUSH')` 会先命中 `[Diag] PUSHNM …`。**
   `lastDiag` 是「从后往前找第一个**包含** needle 的行」，而 `PUSHNM` 行含有 `[Diag] PUSH` 子串。
   于是 A 段（推 + 凑成字）会读到 PUSHNM 的回弹样本 ⇒ 断言变成一个「永远不成立」的假失败。
   修法：`needle` 与 `tag` 分开传，PUSH 的 needle 带**尾随空格**。

3. **`findPush` 的样本退化**（见 §2.2）—— 不修的话，A 段断言的其实是「被推的牌会动」。

另：`tools/gen-tile-roles.py` 生成 `tile-roles.js` 时，`'\n'.join(一个字符串)` 是按**字符**拆
（Python 经典笔误），产出文件第 87 行会多出一个孤零零的 `"`；已改成按行显式构造。
