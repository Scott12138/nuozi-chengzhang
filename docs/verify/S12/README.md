## 三、宝牌的三层设计

### 规则层（`core/`）
- 宝牌**不合成字**，它干的是另一件事：**消掉自己 + 额外送玩家一对普通牌**
- 送的那一对**必须能合成**（见上表第 1 条），且**拆掉之后每个字的偏旁/部件数量仍守恒**
- 被送掉的那一对**要计入它对应的字**的目标条 —— 否则那两个字永远差一对，关卡通不了

### 素材层（`design/ink-treasure.js`）
- **为什么不走 AI 生图**：① 纸底色调差一个色温，一眼看出「从别的图库贴过来的」；
  ② 边缘没有 `#chenZhi` / `#xianWei` 帘纹与陈纸颗粒；③ 128px 下细节糊成一团。
  所以宝牌与字牌**共用同一套 SVG 渲染管线**。
- **器物用实心剪影，不用写意笔触**：字牌的 `imagery.js` 是"几笔淡墨挂在字旁边"（有字的墨骨托着）；
  宝牌没有字、只有 128px，写意笔触会退化成"几道灰痕"。
- **三套候选配色**：`zhu` 朱漆宝匣（#a8322a + #d8b45c）/ `wu` 乌木描金（#2f2b28 + #c9a24a）/
  `sajin` 洒金宣（#e9dcbd + 洒金箔点 + #a8322a 朱砂框）。当前 `TREASURE_PALETTE = 'zhu'`（**暂定，待拍板**）。
- **★ 显式包围盒**：不能从 path 的 `d` 里正则抠数字算包围盒 —— 算盘的算珠用了 `A`（椭圆弧），
  参数里带 `34 34 0 1 0` 这种**不是坐标**的数字，抠出来会把包围盒撑错位置
  （表现为"算盘比别人小一圈且偏向一边"，且**不报错**）。

### 表现层（`ui/GamePage.ts`）
- 读法：「**结构不变，只换一个色块**」。普通牌 = 米白宣纸 + 浓墨字 + 右下朱砂；
  宝牌 = 米白宣纸（同族）+ 中心漆面 + 描金双框 + 器物反白。
  整盘仍是宣纸调子，而**只有它是实心色块**，扫视时自己跳出来。
- 三段演出（不是一次全消）：若把 240ms 那段省掉，玩家会读到"我凑了个宝牌，然后场上少了两张牌"——
  而不是"我凑了个宝牌，它替我把『木+午』消成了『杵』"。**后者才是这个机制的价值。**

## 四、★ 落地时挖出的真问题（六个，全部静默或指错方向）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 运行期 `Bundle resources doesn't contain tiles/x_ch1_01/spriteFrame`，宝牌画不出来 | 烘完宝牌后**漏跑 `fix-tile-meta.js`** → 新 PNG 的 meta 还是 `type: "texture"`（只有 Texture2D、没有 SpriteFrame 子资源） | 补跑；并在本文档 §六 的复现清单里把它标成"重烘贴图**必跑**" |
| 2 | `[Diag] TREASURE none` 被读成"本关没有宝牌走法" | 该行**有歧义**：`findTreasureMove` 只找"挪一步"的走法，两张宝牌一开局就对齐时它也返回 null —— 而那不是"没得消"，是**该点不该拖** | 补 `[Diag] TREASURE direct`（与 `REACH direct=` 同一条教训） |
| 3 | 冒烟报"20 手之后仍拿不到宝牌走法"，可那一局**已消 9/15、剩牌 14，盘面明明活着** | `SUGGEST none` 同样有歧义：`findSuggest` 只在**空格**里找落点，"把 A 挪到它搭档身上"永远给不出来。前置消除只认 SUGGEST，撞上"只剩点一下的走法"就罢工 | 补 `[Diag] DIRECT`（给出**是哪一对**），前置消除改为「有 SUGGEST 就拖、没有就按 DIRECT 点」 |
| 4 | 连拍里"金线圈住赠品"那张**只有宝牌自己**，赠品连边都没进框 | 裁剪框是"围着宝牌那一带"的，而**赠品在盘面随机位置** | 宝牌动作改为**整屏**密采样 storyboard |
| 5 | 请求 +620ms 的帧画的是 560ms 之前的状态 | `captureScreenshot` 整屏一次 120~190ms，且会**抢占合成器**（抓图期间引擎不产新帧）→ 拿回来的帧落后请求时刻 **150~400ms 且不稳定** | 不追求"每张对准某一刻"，改成每 ~220ms 一张的**密采样**；精确时间轴改用 `rec:` 录屏 |
| 6 | 自检里"两张宝牌没对齐"的反例断言**失败** | 我把反例构造错了：`lineClear` 只要求"中间没有牌"，**不等于相邻**。`spread` 那张盘两张宝牌同列、中间只是空格 → 本来就 lineClear | 要构造"没对齐"必须让两张牌**既不同行也不同列**（用斜对角盘面） |

## 六、复现（按顺序，每步都有自检）

```bash
# ── 素材链（只改了宝牌图案/配色时从这里开始）──
python3 tools/preview-treasure.py                  # 三套配色 + 八件器物试样页

# ── 贴图链（★ 烘完必须跑 fix-tile-meta，否则宝牌是空的，且不报错）──
python3 tools/make-tile-atlas.py                   # 256 张 = 248 字牌 + 8 宝牌
node tools/fix-tile-meta.js                        # ★★ 漏了这步 → 运行期 "doesn't contain xxx/spriteFrame"
bash tools/cocos-build.sh wechatgame release       # 首轮让 asset-db 导入
node tools/fix-tile-meta.js                        # 幂等；导入后可能又冒出新 PNG
bash tools/cocos-build.sh wechatgame release       # 二轮才是真产物
python3 tools/build-size-report.py                 # ★ 验收：主包 ≤ 4MB
node tools/core-selftest.js                        # 173 条断言

# ── 冒烟（★ 必须 debug，release 剥掉日志；宝牌只在 tr>0 的关卡 = L3 起）──
bash tools/cocos-build.sh web-desktop debug
bash tools/smoke-run.sh web-desktop /tmp/s12-tr \
  "unlock:3:3" "time:900" "wait:2500" "d:0,-534" "p:chap" "d:0,335" "p:map" \
  "wait:1400" "d:255,77" "p:game" "wait:3800" "xform" "treasure"

# ── 真机码 ──
bash tools/wechat-preview.sh game-5-chaizi release docs/verify/S12/device
```

> `d:255,77` 是**地图页 L3 节点中心**。换算：`x720 = X372 × 1.9355 − 360`（画布宽 600 时，
> 即 `PS = 600/720`、`cx = 300`）。L3 在 372 空间是 `x=283.7+34.1=317.8, y=316.7+34.1=350.8`
> → `d:(255, 77)`。⚠️ 旧文档里的 `L3 d:255,131` 是"标题下移"之前的坐标，**已作废**。
