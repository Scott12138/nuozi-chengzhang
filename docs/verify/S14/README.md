## 二、演出延后：器物与金圈**不再共存**（本轮唯一需要运行时核对的改动）

### 原来的问题
第一段只留 **240ms**，而器物显形（`treasureCrest`）本身要演到 **~770ms** 才收完 ——
于是金圈与金线**正好画在器物贴图底下**。玩家读到的是
「我凑了个宝牌，然后场上少了两张牌」，
而不是「它替我把『竹+前』消成了『箭』」。**后者才是这个机制的全部价值。**

### 新时序的锚点不是拍脑袋的数，是 `treasureCrest` 的生命周期

| 时刻 | 发生什么 | 代码位置 |
|---|---|---|
| 0 | 器物开始涨（0.4s → 峰值）＋ 撞击环 | `treasureCrest` 的 tween |
| 430 | 器物**开始收势**（`TREASURE_CREST_SINK_MS`，补一枚由大收小的金环） | `GamePage.ts` |
| ~770 | 收到 `MELT_OUT` | 同上 |
| **820** | **器物节点 destroy** | `this.timer(… crest.destroy(), 820)` |
| **840** | 金圈 + 金线**才开始**（`TREASURE_POINT_MS` = 820 + 20ms 缓冲） | `resolveTreasure` |
| 1260 | 赠品撞掉（`TREASURE_TAKE_MS`） | 同上 |
| 1780 | 清理 + 判胜负（`TREASURE_CLEANUP_MS`） | 同上 |

整段演出由 1080ms 撑长到 **1780ms** —— 但只在**一次宝牌成对**上发生，一关最多 3 次。

### 多出来的 400ms 全用来做「圈住」这一下的动态
金线从一头**生长**过去（220ms `quadOut`）→ 两枚金圈**收紧**套住 →
每张牌各自炸开一小圈（静态金圈的"圈住"感很弱）→ 两张牌被**挑起**一下。

### ★ 运行时证据

`smoke-treasure/_sheet-treasure-timeline.png`（6 帧时间线）与 `_cmp-640-vs-880.png`：

| 帧 | 器物 | 赠品 前/竹 上的金圈 |
|---|---|---|
| +0ms | 无 | 无 |
| +200ms | **有（大）** | 无 |
| +420ms | **有** | 无 |
| +640ms | **有（收势中）** | 无 |
| +880ms | **已消失** | 无（20ms 空档） |
| +1200ms | 无 | **有：两枚金圈 + 金色虚线** |

→ **器物可见的每一帧都没有金圈；金圈出现的每一帧都没有器物。** 用户拍板的意图成立。

## 三、开局有解：每关 4 颗离线验证过的种子

### 为什么不是"多试几次发牌"
实测**随机开局**的有解率只有 **84%**（36 关 × 8 盘 = 288 盘：有解 242 / 真无解 36 / 未算完 10），
**20 关存在"随机开局即死局"**，连第 1 关都只有 79.2%（19/24）。
所以改成：每关预置 **4 颗**离线验证过有解的种子，进关时从中随机挑一颗。

### 做法
- 生成器 `tools/gen-level-seeds.js`：候选由 `new Rng(20261003 + lv.n * 100003)` 派生
  （**不用时间戳**，任何机器跑出来同一批）；判据固定 `bonus: 'none'`。
- **同一关 4 颗盘面指纹必须互不相同**（否则等于只有 3 种开局）；凑不齐就报错退出，不静默降级。
- 产物 `core/LevelSeeds.ts`（勿手改）+ 本目录 `level-seeds.json`。
- `GamePage.pickSeed()`：`forceSeed()` > 种子表随机挑 > 兜底 `seedFrom`（带显式 log）。

### 盘面指纹 `Board.fingerprint()`
FNV-1a 32 位 → 8 位十六进制，对「每张牌的 `id@r,c`」排序后求哈希。
种子表里存下每颗种子**当时**的指纹；自检重算比对 ⇒
**"发牌路径动过了 ⇒ 那 4 局已不是当初验的那 4 局"** 会在自检里当场暴露。

### 复核结果
```
node tools/gen-level-seeds.js --verify
→ L3 ~ L38 每关 4 颗：✓ 全部有解，指纹一致     （152/152，约 15s）
node tools/core-selftest.js
→ 断言通过 183 条，失败 0 条（含新增 7 条种子表断言）
```

## 四、工具侧：本轮修掉两个「工具与引擎走两套规则」的根因

`tools/solve-exact.js` 的对账口径从 **177/222** 提到 **221/221 = 100%**。

| 根因 | 症状 | 修法 |
|---|---|---|
| **规划器没算宝牌赠品** | `greedy`/`greedyPlan` 直接调 `applyAction`，而 `a.bonus` 从没被赋值 ⇒ 规划时"宝牌只消两张"，回放时"还额外送一对"，两盘面从第一次凑成宝牌起分道扬镳 | 新增 `settle()`：`a.bonus === undefined`（没问过）→ 问真源并写回；`null`（问过、无可送）；数组。`applyAction`/`undoAction` 照它做 |
| **规划器太弱被误报成"这盘走死了"** | L4 某盘：一次随机顺序贪心成功率仅 **2.5%**，40 次全败概率 36%；而 DFS 只用 **2595 个节点**就找到 16 步解 | 新增 `planFor()`：先换 `tries` 个随机顺序贪心（0.4~3ms/次），全败再上 DFS。返回 `via`：`'greedy'`/`'dfs'`（真死局）与 `'budget'`（**没算完，绝不能说成死局**）分开记账 |

### 两个口径，别混用
| 口径 | 含义 | 结果 |
|---|---|---|
| `--bonus none` | 不给赠品。问的是「**这张牌面本身是不是死局**」 | **221/221 = 100%**（同时是工具对账档：规划器与回放同规则，必须 100%） |
| `--bonus real` | 赠品现抽（真机语义） | **201/221 = 91%** ⇒ 赠品有 **9.0%** 概率把可通关带进死局 |

## 七、已知遗留（**未修**，等用户拍板）

**`GamePage.reshuffleRemaining()` 的重排判据太弱。**

```ts
// GamePage.ts ~2696
if (this._board.hasDirectMatch(this._pair)
    || this._board.findSuggest(this._pair, this._rng)) return true;   // ← 只查"至少有一对能消"
```

它保证的是「**至少有一对能消**」，**不保证重排后整盘可解**。
而用户这次选的正是「不改机制，靠重排兜底」——所以这条兜底路径的可信度直接取决于这个判据。

后果：玩家点「看广告重排」后看到「盘面已重排」（一个正反馈承诺），
却可能**只消掉一对又被卡住**，于是要再点一次广告。
（`afterAdReshuffle()` 已经处理了"返回 false 就把弹层立起来"，
所以玩家不会被丢在弹层外面 —— 这是体验问题，不是卡死问题。）

### 三个候选修法（供拍板）
| 方案 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 把「整盘可解」判定搬到 `core/` 里（新增 `core/Solver.ts`），让 `GamePage` 与 `tools/solve-exact.js` **共用同一份真源** —— 与项目既有的"不复刻规则、直接 require 真源"原则一致 | 需把 DFS 从 JS 工具搬成 TS；要定运行期时间预算（DFS 实测 2595 节点/盘，量级不大） |
| B | 判据加严但仍在 `GamePage` 内：如"连续 N 次随机顺序贪心都能全清"才算有解 | 便宜，但仍是**另一套规则**，会重演本轮"两套规则"的老问题 |
| C | 不改判据，改为**重排后立刻校验一次**，不行就再重排（把 30 次尝试用满） | 最省事，但"能不能中"仍是概率，最坏情况仍会给玩家一个假承诺 |
