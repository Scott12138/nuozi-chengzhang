## 三、竖条端头：为什么必须看 dpr，而不是"再调细分段数"

**症状**：章节卡左侧那条渐变竖条的上下端头，在放大截图里像被**硬平切**了一刀，还带一级台阶。

**两个真根因（都已修）**
1. `rect()` 拿到**负宽度**不会"什么都不画"，而是按 `x` 与 `x+w` 连成一个**反向矩形** ——
   竖条 4 设计px 宽、圆角 17 设计px，相减为负 → 整块颜色被画到竖条右边、扎进卡片内部约 25 实现px。
2. 每条色带取上下两端内缩量的**较大者** = 把圆弧量化成台阶。

**正解**：每条色带按**上下两端各自的弧线 x** 画成**梯形**（不是矩形），边界连成一条连续折线。
竖条在距卡片顶边 `d = r − √(2rw − w²)`（r=17、w=4 设计px → d ≈ 6 设计px）处收成尖。

**一个必须记住的判据上限**：竖条只有 8 实现px 宽，收尖处那条斜线在 **dpr=1** 的画布上
只剩 1px 去铺 —— 放大 20 倍看到的是「每格 1 个设备像素」的**量化台阶**，那是采样极限。
实测把圆角段从 8 段加到 20 段有可见改善，**20 段 → 40 段几乎不动（同一画面 PNG 只差 4 字节）**。
所以：

* `对照-竖条端头-dpr1-vs-dpr3.png` —— 同一处端头，左 dpr=1（台阶）、右 dpr=3（平滑斜线）。
  **同一份几何**，差别只在渲染像素密度。
* `放大-竖条上端-dpr3.png` / `放大-竖条下端-dpr3.png` —— 高密度下收尖处是干净的斜线。
* `放大-竖条上端-dpr1.png` / `放大-竖条下端-dpr1.png` —— 低密度对照，用来说明那不是代码问题。
* `对照-竖条端头三方案.png` —— 拍板时 A/B/C 三个方案的对照（最终选 **B · 跟随卡片圆角**）。

> 为此给冒烟工装加了 `SMOKE_DPR`（默认 1）：`deviceScaleFactor` 以前写死 1，
> 导致所有亚像素细节都只能在 dpr=1 下判。坐标全走 CSS px，所以调它不影响任何 `d:` 换算。

## 四、`seed:` —— 把「抽奖式断言」变成确定性回归

发牌种子是 `seedFrom(关号)`，而它把 `Date.now()` 混了进去（`core/Rng.ts`），
**所以每一局的盘面都不一样**。而「卡住 → 看广告重排」这条链路
**只在盘面自己走死时才出现** —— 实测同一条命令：

| 局 | 结果 |
|---|---|
| 第 1 局 | 拖 6 步后只剩「已对齐、点一下就能消」的一对 → **没卡住**（且旧工装误判成"拿不到建议"） |
| 第 2 局 | 拖 9 步**直接通关** → 没卡住 |
| 第 3 局 | 拖 8 步卡死 → 弹层 ✅ |
| 第 4 局 | 拖 7 步卡死 → 弹层 ✅ |

于是 `gate:卡住了` 变成了掷骰子：失败了还分不清是"代码坏了"还是"这局恰好没走死"。

**修法**（两处，都很小）
1. 游戏侧：`GamePage` 里读 `globalThis.__CHA_SEED__`，设了就钉死发牌种子；
   并在「开局就绪」那行日志里回显 `· 种子=force:<n>`，可当场复核。没设时行为与之前逐字节一致。
2. 工装侧：新增 `seed:<n>` 动作写入该全局变量，**必须写在 `unlock:` 之后**（unlock 会重载页面，重载清全局变量）。

**搜索结果**：`seed=4` → 拖 7 步进真死局（日志里 `[Diag] REACH direct=0 suggest=0 → 真的卡住`）。
以后每次回归都重放这一局。

## 五、`REACH` —— `SUGGEST none` 的歧义害我白查一轮

`Board.findSuggest` 的候选落点来自 `reachableCells`，而它**只含空格**。
于是一对已经同行/同列相邻、随时能点掉的牌，是**没有"挪"的解法**的 ——
想把 A 挪到 B 身上？那一格被 B 占着，根本不是合法落点。

所以 `SUGGEST none` 同时对应两种完全不同的局面：

* `direct=1` → **还活着**，只是该「点」而不是该「拖」；
* `direct=0` → **真的卡住**，这时 `checkDeadlock` 才会弹「看广告重排」。

旧工装的 drag 循环只认 `SUGGEST`，遇到前者直接收工，看起来就像"卡住弹层没弹"。
现在：游戏侧 `diag()` 多打一行 `[Diag] REACH direct=? suggest=? → …`；
工装侧遇到 `direct=1` 时改成**逐个点一遍场上的非干扰牌**（点中哪张由 STATE 序号是否变大判定），
点完状态仍不动才算真卡住并报 ❌。

## 六、版式逐值比对（`版式逐值比对.txt`）

| 页面 | 主表项数 | 超容差 | 说明 |
|---|---|---|---|
| `chap` 章节选择 | 7 | **0** | |
| `map` 关卡地图 | 20 | **0** | |
| `play` 对局页（L1，4 个目标字） | 18 | **0** | 与设计稿同款单行摆放 |
| `play` 对局页（L3，5 个目标字） | 18 | 3 | ⚠️ 见下 |

**L3 那 3 项不是 bug，是关卡数据的不同**：设计稿量的是 **4 个目标 chip 单行**（枪/棍/锤/钩），
而 L3 有 **5 个**目标字 → `.goal-bar` 换行成两行（高 74.9 vs 设计 40），
于是它下方的 `.tips`（dy 34.9）与弹性块 `.board-wrap`（dy 34.7、高度被吸收）跟着位移。
`.goal-bar` 自身 `dx/dw` 均为 0，底锚块（`.made-strip` / `.tool-bar` / `.tool[*]`）全部 ✔，
即"多出来的 34.9 设计px 由弹性块完整吸收"，内部是自洽的。

**结论**：判对局页版式要挑**目标字 ≤4 的关**（L1）；L3 的差异是预期行为，已在表里标注。
